# 技术架构设计

## 技术栈选择理由

项目使用微信小游戏、TypeScript、Canvas 2D 和自研轻量框架。TypeScript 提供类型约束，适合维护光线、关卡、实体和平台适配层。Canvas 2D 足以表达光线、镜子、三棱镜和轻量 UI，同时包体小、启动快。

## 为什么不用重型引擎

Unity、Cocos、Phaser 能提升复杂游戏开发效率，但第一版目标是轻量上线和练习 Web Coding。重型引擎会带来更大的包体、更多构建约束和审核排查成本。当前玩法以 2D 几何和 Canvas 绘制为主，自研小框架更容易控制性能和结构。

## 分层架构说明

- `app`：游戏入口协调器，负责初始化平台、场景、循环。
- `core`：循环、时间、事件、调试等基础设施。
- `scenes`：首页、游戏页、关卡选择等场景。
- `entities`：实体类型定义，不包含具体业务流程。
- `rules`：光线传播、反射、分光、命中和胜利判定。
- `renderer`：Canvas 绘制层。
- `input`：触摸事件封装。
- `ui`：Canvas UI 组件。
- `audio`：音效与音乐管理。
- `levels`：关卡配置。
- `platform`：微信平台和本地能力适配。
- `utils`：数学、id、断言等工具。

## 每个目录职责

核心原则是单向依赖。规则系统不依赖渲染器；渲染器只读取状态；平台层封装所有 wx API；音频通过事件总线响应事件，不嵌入玩法规则。

## 数据流

关卡配置进入 `GameScene` 后生成实体状态。输入系统改变可操作实体。规则系统根据实体计算光线结果。渲染器读取实体和光线结果绘制画面。命中和胜利事件通过 `EventBus` 通知 UI 与音效。

## 事件流

事件总线承载跨层通信，例如：

- `level:start`
- `ray:split`
- `target:hit`
- `level:win`
- `ui:click`
- `audio:muteChanged`

事件载荷必须保持小而明确，不传递平台对象。

## 渲染循环

`GameLoop` 持有时间对象，每帧执行：

1. 更新时间。
2. 当前场景 `update(deltaTime)`。
3. 清屏。
4. 当前场景 `render(renderer)`。

Debug 模式可以记录帧耗时和光线数量，发布版本默认关闭。

## 输入处理

`InputManager` 只处理触摸开始、移动、结束，并把坐标标准化。它不直接依赖具体场景业务，也不直接调用 wx API。微信触摸事件由 `WechatPlatformAdapter` 接入。

## 平台适配

`PlatformAdapter` 定义 Canvas、循环、触摸、本地存储等接口。`WechatPlatformAdapter` 是第一版唯一实现。后续 Web 调试适配可以实现相同接口，不改玩法规则。

## 后续扩展点

- 增加真实折射或颜色目标。
- 增加 Web 调试入口。
- 增加关卡编辑器。
- 增加对象池和离屏 Canvas 缓存。
- 增加自动关卡验收脚本。
